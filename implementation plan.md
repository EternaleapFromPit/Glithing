# Runtime Dispatch and Framework Completion

## Status
Generic monomorphization, constrained generic indexing, service-registration compat surface expansion, and async scheduler compat surfaces are complete. Slice 2 and 3 compat additions landed July 2026. Target-typed `new()` resolution (Slice 5) and DI-registration-aware interface resolution (Slice 6) landed August 2026 — the Conduit IntegrationTests project bundle now compiles cleanly end-to-end. Slice 7 (the `GET /articles` crash) is fixed: two genuine compiler bugs (`&&`/`||` never short-circuited; JSON list serialization didn't null-check) were root-caused via `cdb` and fixed — the live app now boots and serves `GET /articles` with HTTP 200. Slice 8 (real `DateTime` + `DbQuery<T>` LINQ methods) landed August 2026, and along the way fixed four more general compiler bugs found by chasing it (explicit-body property getters silently discarded, `double`→integer casts entirely unimplemented, whole-number `double` literals emitted as invalid LLVM IR, and `DateTime` having been silently hardcoded to `string` at parse time this whole project). Slice 9 (making `IQueryable<T>` resolve to its real underlying type across a method boundary) landed August 2026 — turned out not to need a new interface-dispatch mechanism at all: a one-line generic-substitution bug in the general method-call lowering path was silently discarding class-level generic specialization (`DbQuery<Article>`) every time a call site also went through the (empty, irrelevant) method-level generic-args substitution step, collapsing it back to the unspecialized placeholder (`DbQuery<T>`) on every chained call. `GET /articles` on the live app now returns HTTP 200 with a well-formed `ArticlesEnvelope` shape end-to-end. Two new, narrower gaps were found and confirmed while verifying this (both documented below, neither started): the live app's `Articles` field still serializes as `null` rather than `[]` for an empty result set (root cause not yet identified — the `DbQuery`/`DbSet`/`ToListAsync` plumbing itself was checked and is not the cause), and primitive numeric `.ToString()` (`int`/`long`/etc.) has no implementation at all and crashes at runtime via a call to an unresolved bare symbol — a pre-existing gap, unrelated to Slice 9, never previously exercised by any test or app path.

### Slice 5 — Concurrent task-runtime memory safety (August 2026)
- Fixed a cross-thread data race on `@glitch_exception_pending`: it was a single process-global LLVM variable used to propagate thrown exceptions up the call stack, but `Task.Run` executes worker closures on real OS threads, so two tasks throwing/completing concurrently could misattribute one task's exception to another. It is now `thread_local` in `src/llvm/runtime.rs`.
- Fixed `release_glitch_string` in `src/runtime.rs` to match the atomic decrement-then-free-if-zero pattern used everywhere else (`glitch_string_release`, `glitch_delegate_release`, `glitch_box_release`); it previously freed unconditionally without decrementing a shared refcount.
- Fixed a use-after-free in `GlitchTask_GetException` (`src/runtime.rs`): it read a task's exception message via a `CStr` borrowed from the exception's own buffer, then freed that buffer via `release_glitch_string` *before* copying the message into a fresh allocation. Under concurrent load the allocator would occasionally hand the just-freed block right back out, corrupting the copy (and tripping Rust's debug-mode UB checks as a crash). Fixed by building the copy before releasing the source.
- Root-caused via `tests::framework_and_xunit::native_task_when_all_propagates_faulted_tasks`, which was intermittently failing/crashing (~11% of runs in a standalone stress-test repro of the same scenario). Verified fixed with 500/500 clean runs of the repro after all three fixes landed.

### Slice 6 — RealWorld (Conduit) end-to-end compile/boot/serve (August 2026)
Goal: get `external/aspnetcore-realworld-example-app/src/Conduit` (a real cloned ASP.NET Core app) to compile, boot, and serve HTTP requests without crashing. Found and fixed six unrelated bugs blocking each successive stage:
- **`await` inside `try`/`catch`/`finally` was hard-rejected** (`src/tir/validation.rs`) even though the recursive ownership-liveness analysis needed to support it was already implemented directly below the rejection, unreachable. Removed the rejection; the async codegen model is a blocking worker-thread gate with all locals stored in a persistent heap state struct, so no additional state-machine work was needed. Unblocks `DBContextTransactionPipelineBehavior<,>.Handle`, MediatR's transaction-wrapping pipeline behavior that runs on every request.
- **Lambda discard parameters collided in LLVM IR** (`src/llvm/delegates.rs`): `(_, _) => true` (a common LINQ/Swagger predicate pattern) compiled both C# `_` parameters to the literal LLVM register `%_`, an illegal duplicate definition. Each parameter now gets a unique positional register name while `emitter.vars` still resolves by the original source name.
- **Duplicate DI temp-name collision** (`src/llvm/collections/services.rs`): resolving the same service type twice via `GetService<T>()`/`GetRequiredService<T>()` in one method body reused the literal prefix `"service_lookup"` for LLVM temp names, producing a duplicate-definition error. Now uses `next_label("service_lookup")` for a unique prefix per call site.
- **Use-after-free freeing array-literal elements** (`src/llvm/collections/basics.rs`): `emit_new_array` retained-or-not per `retain_for_store`'s ownership rules, then *unconditionally* called `emit_temporary_drop` afterward for any "temporary-shaped" element (`NewObject`, `Call`, `Await`, nested array/collection literals, etc.). For elements `retain_for_store` correctly declined to retain (because a fresh temporary already owns its sole reference, which the array should just inherit), the extra drop freed memory the array still held a pointer to — a real, general array-literal bug, not specific to any one type. Caused nondeterministic `STATUS_HEAP_CORRUPTION` crashes at startup. Fixed by only pairing the post-store drop with the one case that legitimately needs it (`Task`, which unconditionally retains first).
- **`Task.Result`/`.Exception` accessed outside `await` leaked the task object** (`src/llvm/stmt_expr/expressions.rs`): for a temporary task source (e.g. `SomeAsyncMethod().Result`), the code retained the task, read the result, then called `GlitchTask_Destroy` exactly once — leaving `refs` at 1 forever (`GlitchTask_Destroy` only frees when its decrement brings `refs` to 0). The already-correct `await` codegen path proved the right pattern: a single unconditional `emit_temporary_drop`, no retain. Applied the same pattern to both the `Result` and `Exception` accessors.
- **Duplicate stdlib class definition across two packages** (`packages/Glitching.AspNetCore/Glitching.AspNetCore.gl`): both this package and `Microsoft.AspNetCore.Authentication.JwtBearer` declared a class named `JwtBearerDefaults` with incompatible shapes (an instance field requiring construction vs. the correct static getter-only property). When both packages loaded into one compilation, the compiler resolved the member against one type's layout while emitting the struct-typed GEP for the other, producing a field access at a fixed near-null offset (`mov rdx, [0x10]`) — a genuine `STATUS_ACCESS_VIOLATION`. Removed the erroneous duplicate (unreferenced anywhere; the real implementation lives in the Microsoft.* package).
- **Off-by-one in the compiler's own smoke-test harness** (`src/realworld_smoke.rs`, not a compiler bug): `GlitchRestHost_Run`'s request counter (`src/runtime.rs`) increments on every *accepted TCP connection*, including a bare connect-then-drop with no HTTP data. The harness's own port-readiness probe does exactly that, silently consuming one of the two request slots budgeted for its two real HTTP checks. Bumped the budget to 3.

Result: the app now compiles, links, boots, and serves `GET /articles` with HTTP 200 without crashing. Two gaps remain, confirmed as pre-existing/documented rather than newly discovered:
- `GET /swagger/v1/swagger.json` returns 404 — Swagger/OpenAPI document generation was never implemented (`SwaggerGenOptions` configuration calls are compat markers per Slice 2's own list; no route is ever registered for the generated document). This is a standalone feature, not a bug fix.
- `/articles` responds 200 but with the literal body `"501 Not Implemented"`, not real JSON — full attribute-routed MVC controller dispatch to real business logic (and EF Core query execution) is the "generated controller routing... still incomplete" gap the README already calls out. The route resolves far enough to avoid crashing, but not to the real controller action.

Verified via `cargo run --bin realworld_smoke` plus manual `cdb`-driven crash forensics (real crashes required `-g -O0` relinks against `target-runtime-link/debug/glitchc.lib` — the compiler's default native build has no debug info) and a series of minimal standalone repros per bug. Full `cargo test`: 306 passed, 0 failed, 1 ignored (unchanged) after every fix.

### Slice 7 — JSON serialization of nested objects and `List<T>`/array fields (August 2026)
Goal: `endpoint_return_supported` required every field of an endpoint response class to be scalar/string — no nested classes, no `List<T>` — so `ArticlesEnvelope { List<Article> Articles; int ArticlesCount; }` (and most other real Conduit response shapes) fell straight back to the `501 Not Implemented` stub before ever reaching the handler body. Implemented real recursive JSON serialization:
- **`[JsonIgnore]` now threads all the way through**: added `attributes: Vec<Attribute>` to `FieldDef` (`src/ast.rs`) — the parser already parsed member attributes for every class member but silently discarded them for plain field declarations while keeping them for constructors/methods. Added `json_ignore_fields: HashSet<String>` to `TypedType` (`src/tir.rs`, populated in `lower_type`, `src/tir/lowering.rs`) and `LlObjectType` (`src/llvm.rs`, populated in `register_object_type` and carried through generic specialization in `src/llvm/generics.rs`). This matters for correctness, not just fidelity: the real `Article`/`Person`/`Comment` domain models have genuine reference cycles (`Comment.Article` back-pointer, etc.) that the real .NET app breaks by `[JsonIgnore]`-ing the back-reference; without honoring it, naive recursive serialization would infinite-loop/stack-overflow the moment real cyclic data was returned.
- **`endpoint_return_supported`** (`src/llvm/endpoint.rs`) is now recursive: `List<T>`/`Array<T>` and nested `Class`/`Struct` fields are accepted if their own fields are (or are `[JsonIgnore]`d), guarded by a `visiting: &mut HashSet<String>` set so a real cycle in the *type graph* doesn't infinite-loop the static check itself (the loop only actually breaks safely at serialization time via `[JsonIgnore]`, not by this check alone).
- **`emit_json_serialize_object`** was refactored: the old inline per-field `match` became a reusable `emit_json_serialize_value(ty, value)`, extended with a `Class`/`Struct` case (null-checked recursive call) and a new `emit_json_serialize_list` (manual loop over `%glitch.list`/`%glitch.array`, comma-joining each serialized element). `[JsonIgnore]`d fields are skipped entirely.
- **Found and fixed two more bugs while wiring this up**, both pre-existing and only reachable once a controller could actually return a class (no prior test exercised that natively):
  - `emit_endpoint_result` built its post-serialization drop-glue call from the *unqualified* type name (`drop_symbol(name)`, e.g. `glitch_drop_ItemsEnvelope`), but `LlObjectType.name` — the name drop glue is actually defined under — always carries a `qualified_name` suffix (`glitch_drop_ItemsEnvelope__g0__t42`), an "undefined value" link error. Fixed to resolve through `object_layout(name).name`, matching the pattern already used correctly elsewhere (e.g. the DI-dependency cleanup loop in the same file).
  - Two `phi` nodes (in `emit_endpoint_result` and the new nested-object case) assumed control returned from a null-check branch to exactly the block they branched to. That was safe when the branch body was flat, straight-line code, but recursive object/list serialization can itself branch (nested null checks, list loops), so the actual predecessor at the merge point is often a different block than the `phi` named, producing an "invalid LLVM IR: instruction does not dominate all uses" link error. Fixed by switching to the `alloca`+`store`+`load` merge pattern already used elsewhere for this exact reason (e.g. ternary-expression codegen), which doesn't care which block did the store.
- Verified via two new native-execution tests: `runs_nested_list_json_endpoint_natively` (a `List<Item>` field, real HTTP JSON output checked byte-for-byte) and `runs_json_ignore_cyclic_reference_endpoint_natively` (a genuine `Parent <-> Child` type cycle broken by `[JsonIgnore]` on a `Weak<Parent>` back-reference, confirming both the cycle-safe static check and the runtime skip). Full `cargo test`: 308 passed, 0 failed, 1 ignored.
- **Result on the real app**: `GET /articles` no longer falls back to the stub — it's now recognized as a supported endpoint shape and returns HTTP 200 with body `null`, because the controller action's `mediator.Send(new List.Query(...))` doesn't actually dispatch anywhere yet. That's the next gap in the chain (generic interface/virtual dispatch, Slice 1), confirmed but intentionally not started this slice.

### Slice 1 — Namespace-qualified type resolution (August 2026)
Investigation revealed the actual blocker wasn't MediatR dispatch logic at all — `emit_mediator_send` already correctly matched a request's compile-time type against `IRequestHandler<TRequest,_>` bases, resolved DI dependencies, and invoked the real handler (confirmed by watching a full call stack reach a real `Handle` method). The real gap: **the compiler had no namespace-aware type resolution**. Every type — nested or top-level — was registered by bare simple name in one flat global map (`env.kinds.insert(ty.name.clone(), ty.kind)`, `src/tir/signatures.rs`), with `namespace` stored but never consulted. Confirmed this collides *in the real app today*: `Create`, `Delete`, `Details`, `List`, `Edit`, `Add` are each declared 2–4 times as feature-grouping classes across different namespaces (MediatR's standard convention of nesting `Query`/`Command`/`Handler` inside a per-feature class), each silently overwriting the previous registration; and unqualified `new Feature.Type(...)` references from outside the enclosing class didn't resolve at all (fell back to an opaque `Unknown` type, silently constructing `null`).

Implemented full namespace-qualified resolution, scoped to minimize blast radius — only types that actually collide are touched, so the overwhelming majority of (unique-named) types are completely unaffected:
- **`TypeDef` gained `enclosing_types: Vec<String>`** (`src/ast.rs`) — the full chain of enclosing simple names, threaded through `parse_type_def` (`src/parser/declarations.rs`, `src/parser/items.rs`) by passing the current type's own name down before each recursive nested-type parse. Added `qualified_type_path(namespace, enclosing_types, name)` as the canonical dot-joined identity.
- **New pass: `src/parser/qualify.rs`**, run once at the end of `parse_program()` (`src/parser/items.rs`) — after this point every downstream consumer (TIR lowering, ownership checking, LLVM codegen) sees an already-disambiguated program, so none of the ~75 existing `type_syntax_to_ir` call sites needed to change. It:
  1. Counts simple-name occurrences across all types; only names appearing more than once get renamed to their full qualified form (`ty.name = "Conduit.Features.Comments.Create.Command"`), recording each renamed candidate's namespace + enclosing chain.
  2. Walks every base-class-list entry, field/parameter/return/local-variable type, and `new X(...)` construction in the whole program, rewriting any reference to a renamed type to the correct qualified form *for the scope that reference appears in* — preferring an exact scope match, then same-namespace, mirroring how nested C# scopes resolve names outward. A reference that stays ambiguous after that is left as-is rather than guessed at.
  3. Handles generic-decorated base strings (`"IRequestHandler<Query,Envelope>"`) by resolving the head and each argument independently and rejoining them.
- **Found and fixed a second, independent bug this surfaced**: `request_type_matches` (`src/llvm/endpoint.rs`), used to match a MediatR request's type against a handler's `IRequestHandler<TRequest,_>` base, fell back to comparing `base_type_name(...)` — the bare last dot-segment — when an exact/suffix match failed. Once colliding types got correctly disambiguated by this slice, two *different* qualified `Command` types both reduced to the same bare `"Command"` and both matched; since the handler search iterates a `HashMap`, whichever handler happened to come first in that run's (randomized) iteration order silently won — a real, then-newly-flaky bug, not a regression in the old sense (the old code had the exact same ambiguity, just masked by types clobbering each other at registration time instead). Fixed by requiring an exact match or a dot-bounded suffix match on the *full* qualified name; removed the base-name fallback entirely.
- Verified via a new native-execution regression test, `resolves_colliding_nested_mediatr_types_by_namespace_natively`: two different namespaces each declare their own `Create` class with its own nested `Command`/`CommandHandler`, and a controller in one namespace calls `mediator.Send(new Create.Command(...))` — confirmed (run 8× to rule out the iteration-order flakiness above) that the correct feature's own handler always wins. Full `cargo test`: 308 passed, 0 failed, 1 ignored — zero regressions across every other existing test, consistent with the fix's scoped, collision-only blast radius.
- **Result on the real app**: the specific `mediator.Send(new Create.Command(...))` call this slice was scoped around now resolves and dispatches correctly (confirmed via direct debug trace: exact constructor-signature match against the right qualified type). The full Conduit app compile test still fails, but now on a *different, confirmed-unrelated, pre-existing* gap: C# target-typed `new()` expressions (`= new();`, used extensively for domain-model collection field defaults — `List<Comment> Comments { get; init; } = new();` appears throughout `Domain/*.cs`) parse to a `"__target"` placeholder type name (`src/parser/expressions.rs`) that is never actually resolved anywhere in TIR lowering — not something this slice's namespace work touches or introduced.

### Slice 5 — Target-typed `new()` resolution (August 2026)
Implemented the gap Slice 1 confirmed as the next blocker: C#'s target-typed `new()` (`SomeType x = new();`, `new Command(new(), other)`) parsed to a literal `"__target"` placeholder type name (`src/parser/expressions.rs`) that TIR lowering never resolved. Fixing this end-to-end surfaced four more pre-existing bugs, each found by chasing the real Conduit app through this one code path:

- **`"__target"` resolution** (`src/tir/lowering.rs`, `Expr::NewObject` handling inside `lower_typed_expr_with_expected`): when `type_name == "__target"`, infers the real type from `expected: Option<&IrType>` — a `List`/`Dictionary` expected type lowers to `NewCollection`; a `Class`/`Struct`/`Interface` expected type resolves to that name; anything else is a clear error naming the unsupported inferred type. `lower_call_args`'s fallback arm (previously `lower_typed_expr` with no context) now calls `lower_typed_expr_with_expected(arg, env, scopes, expected)` so constructor/method arguments propagate their expected parameter type — the mechanism target-typed `new()` needs when used inline (`new Create.Command(new(), slug)`).
- **Instance field initializers were never applied at all** (only static ones were, `src/tir.rs`): `List<T> Items { get; init; } = new();` silently did nothing, leaving every such field null at runtime. Fixed via a new shared helper, `effective_constructors(ty: &TypeDef)` (`src/tir.rs`): for a type with no explicit constructor but at least one instance field initializer, synthesizes the implicit parameterless constructor C# gives it, prepending the field-initializer assignments to every constructor's body. Used identically by both `populate_constructor_signatures` (`src/tir/signatures.rs`, registers the call-site-resolvable signature) and `lower_type` (`src/tir/lowering.rs`, actually emits the constructor). These two were originally implemented as separate, drifted synthesis logic — the call-site registry didn't know about the synthesized constructor lowering created, so `new Container()` allocated the object but never actually invoked the constructor that would have initialized `Items`, leaving it null despite the constructor itself being emitted correctly. Unifying them into one helper fixed it.
- **Field reassignment leaked the previous owned value** (`src/llvm/stmt_expr/statements.rs`, `TypedStmtKind::AssignTarget`'s `Field` case): assigning over a field only dropped the old value for `Class`/`Struct` objects and strings — `List`/`Dictionary`/`Array`/`Task`/`Nullable`/delegate/boxed-`object` fields were never released on overwrite. Invisible before this slice because such fields were always still-null (the bug above) at the point of first reassignment; the field-initializer fix newly exposed real leaks (`holder.Items = tasks;` after a `= new List<T>()` initializer leaked the initializer's list). Fixed by extracting the local-variable drop logic (`emit_var_drop`'s type-driven match, `src/llvm/objects.rs`) into a shared `emit_owned_value_drop(ty, value)` used by both scope-exit local drops and field-reassignment drops.
- **Nested types with the same bare name in the same namespace were silently merged** (`merge_type_declarations`, `src/parser/helpers.rs`): the dedup/merge key was `(package_id, namespace, name)`, omitting `enclosing_types`. Under MediatR's per-feature nesting convention, `Articles.Edit.Command` and `Articles.Delete.Command` share `namespace = Conduit.Features.Articles` and `name = Command` — different types, but the same key — so they were merged into one `TypeDef` with concatenated constructors, and only the *first*-encountered one's `enclosing_types` survived. This made the Slice 1 namespace-qualifier blind to most of these nested types entirely (there was only ever one merged "Command" per namespace to qualify, not one per enclosing class), and is why a downstream `new Edit.Command(...)` reference couldn't find a matching constructor signature at all. Fixed by adding `enclosing_types` to the merge key.
- **The Slice 1 namespace-qualifier's scope-disambiguation heuristic didn't handle cross-namespace consumers** (`Resolver::pick`, `src/parser/qualify.rs`): it required either an exact namespace match or a unique surviving candidate to resolve an ambiguous reference. A test file in `Conduit.IntegrationTests.Features.Articles` referencing `Edit.Command` (declared in `Conduit.Features.Articles`, one of two `Edit` classes in the app) matched neither — different namespace, and `Command` collides across the *other* `Edit` class too (`Conduit.Features.Users`). Added a fallback: pick the candidate whose namespace shares the longest trailing-segment run with the caller's namespace (`common_suffix_len`), which correctly picks the production namespace a mirrored test namespace is testing, and stays unresolved (previous behavior) on a genuine tie.
- **Generic/specialized type names could get namespace-prefixed twice** (`qualified_name` in `src/llvm/helpers.rs`, `qualified_type_symbol_name` in `src/tir/signatures.rs`): both unconditionally prepended `namespace.join(".")`/`namespace.join("_")` to a type's name — correct for the common case, but for a type the Slice 1 qualifier already renamed to its full `namespace.enclosing.name` form, this produced `Conduit.Features.Articles.Conduit.Features.Articles.List.QueryHandler`. Only surfaced once the merge-key fix above stopped masking these types from generic specialization. Fixed by skipping the prepend when `name` already starts with the namespace prefix.

Verified via `tmp/target_new_repro.cs` (instance field initializer + target-typed `new()`, runs correctly natively) and the full `cargo test` suite: 308 passed, 0 failed, 1 ignored — zero regressions. The Conduit integration tests project (`compiles_conduit_integration_tests_project_file_through_llvm`) now gets substantially further and fails on a new, confirmed-unrelated gap: `resolve_interface_implementation` (`src/llvm/endpoint.rs`) requires exactly one concrete class implementing an interface to resolve a mediator handler's constructor dependency, but the IntegrationTests bundle compiles both the production `CurrentUserAccessor` and a test double `StubCurrentUserAccessor` (`tests/Conduit.IntegrationTests/StubCurrentUserAccessor.cs`) implementing `ICurrentUserAccessor` — real ASP.NET Core resolves this via DI registration order/test-host overrides, which this compiler doesn't model. Not started this slice; became Slice 6.

### Slice 6 — DI-registration-aware interface resolution (August 2026)
Fixed the gap Slice 5 confirmed as the next blocker, then found and fixed three more bugs it led to:

- **DI registration lookup now takes priority over structural interface search**: `resolve_endpoint_dependency_name` (`src/llvm/endpoint.rs`) now tries `resolve_registered_service_implementation` (an existing lookup against explicit `services.AddScoped<TInterface, TImpl>()`-style registrations, already used by `emit_service_provider_lookup`) before falling back to `resolve_interface_implementation`'s "exactly one class implements this interface" structural search — matching the existing pattern used elsewhere for the same problem.
- **DI registrations are now collected in an order-independent pre-pass** (`collect_service_registrations` + walker, `src/llvm/collections/services.rs`, called from `emit_typed_program` in `src/llvm.rs`): registrations were previously only recorded as a side effect of *emitting* the statement that calls `AddScoped`/`AddTransient`, so a mediator dependency lookup compiled earlier in program order than the `ConfigureServices`-style method that registers it would never see the registration. A lightweight scan-only walker (records registrations, emits no IR) now runs over every function/method/constructor body before any code is actually emitted, so lookups no longer depend on incidental compilation order. This is what actually fixed `ICurrentUserAccessor` resolving to the single production `CurrentUserAccessor` even with `StubCurrentUserAccessor` also in scope (the stub is never DI-registered — test code constructs it directly — so it was never a real candidate to begin with; the true bug was that the *real* registration wasn't visible yet).
- **Mediator-dependency drop calls used the wrong symbol** (`src/llvm/endpoint.rs`, the dependency-injection loop inside the object-allocation path used by DI-driven endpoint thunks): the post-construction cleanup call used the *unresolved* dependency name (bare `"CurrentUserAccessor"`, as returned by a registration lookup) to compute `drop_symbol`/`destroy_symbol`, instead of the object's actual registered name (`"CurrentUserAccessor__g0__t329"`) — producing a link error, `undefined value '@glitch_drop_CurrentUserAccessor'`. This was a latent bug (the code never normalized the name through `object_layout` the way the allocation call two lines above it already did) that only surfaced once the DI-registration fix above could return an unresolved bare name for the first time. Fixed by resolving through `object_layout` before computing the drop symbol, mirroring the existing pattern.
- **Polymorphic mediator dispatch forced every candidate handler to share one response type** (`emit_mediator_runtime_dispatch`, `src/llvm/endpoint.rs`): when a `Send()` call's request is statically typed as the `IRequest` marker interface itself (e.g. inside a generic pipeline behavior wrapping every request), the compiler builds a runtime type-check chain trying each handler in turn. The response type used to validate *every* candidate handler in that chain was taken from only the first (alphabetically sorted) candidate — so any handler whose own response type differed from that first one (a near-certainty once the merge-key fix from Slice 5 correctly split what used to be one merged "Command" per namespace into one per enclosing feature class, each with its own response type) failed a mismatch check that was never actually true for that handler. Fixed by validating each candidate against its own inferred response type instead of a single shared one.

Verified via the full `cargo test` suite: 309 passed, 0 failed, 1 ignored — the Conduit integration tests project now compiles cleanly to LLVM IR (`compiles_conduit_integration_tests_project_file_through_llvm` passes), zero regressions elsewhere.

### Slice 7 — Fixed the `GET /articles` crash: two genuine short-circuit and null-safety compiler bugs (August 2026)
Root-caused via `cdb` (relinked with `-g -O0` against `target-runtime-link/debug/glitchc.lib`, the established debugging pattern) — running the compiled main `src/Conduit` app directly and sending it a real `GET /articles` request, since this was the first time this request had ever reached real handler execution (every prior verification of "GET /articles returns 200" predates target-typed `new()` support, so the app couldn't fully compile until Slice 5, and dispatch only started reaching a request's *real* handler body after Slice 1). Found and fixed two unrelated, genuine bugs, each a fresh crash surfaced only after fixing the previous one:

- **`&&` and `||` never actually short-circuited** (`TypedExprKind::Binary`'s `And`/`Or` case, `src/llvm/stmt_expr/expressions.rs`): both operands were unconditionally evaluated and only *then* combined with a plain `and`/`or` on the two already-computed booleans (`emit_logical_value`, `src/llvm.rs`). This is a serious, general bug — it breaks the single most common C# null-guard idiom, `x == null || x.Field`, by evaluating `x.Field` even when `x` is null. First crash: `System.gl`'s own `IsNullOrWhiteSpace(value) => value == null || value.Length == 0` dereferencing a null `value` inside `.Length`'s `strlen`-based implementation, called from `List.QueryHandler.Handle`. Fixed with a new `emit_short_circuit_logical` helper implementing real branching (alloca+branch+merge, the pattern already established for ternary/nested-JSON codegen elsewhere in this file): the right operand's code is only emitted on the branch where it's actually needed, and its temporary-drop only runs when it was actually evaluated. Verified with a 5-case native repro (`&&`/`||` on both sides, confirming both correct short-circuiting *and* that the non-elided side still evaluates when required) plus the exact `s == null || s.Length == 0` pattern with `s = null`. (The AST-level `Expr::Binary` path in the same file has the identical bug but was confirmed dead code — `LlvmEmitter::emit_program`, its only possible entry point, is never called anywhere — so it was left alone.)
- **JSON serialization of a `List<T>`/array field never null-checked it** (`emit_json_serialize_list`, `src/llvm/endpoint.rs`): unconditionally dereferenced the list pointer to read its length/data, unlike the `Class`/`Struct` case one branch above it in the same function (`emit_json_serialize_value`), which already null-checks correctly. A `List<T>` field can legitimately be null — in this case `Article.Comments`, reached while serializing `ArticlesEnvelope.Articles`. Second crash, found immediately after the first fix landed. Fixed with the same alloca+branch+merge null-guard pattern the `Class`/`Struct` case already uses, rendering `null` for a null list instead of dereferencing it. Verified with a native repro serializing an explicitly-null `List<Item>` field, producing `{"Items":null,...}` instead of crashing.

Verified via the full `cargo test` suite: 309 passed, 0 failed, 1 ignored, zero regressions — plus `cargo run --bin realworld_smoke`, which now gets past `GET /articles` (HTTP 200) and only fails on the already-documented, unrelated Swagger gap (`GET /swagger/v1/swagger.json` returns 404 — never implemented, tracked separately below).

### Slice 8 — Real `DateTime`, real `DbQuery<T>`/`DbSet<T>` LINQ methods, and four more general compiler bugs found along the way (August 2026)
Scoped from Slice 7's finding (`/articles` response was `{"Articles":null,...}` instead of `[]`), confirmed as three compounding gaps — `DbSet<T>.Include` losing its type via the compiler's untyped-fallback mechanism, `DbQuery<T>` missing `OrderBy`/`OrderByDescending`/real `Skip`/`Take` entirely, and `DateTime` being a non-functional placeholder — user chose to fix all of it, including a complete `DateTime`. Implementing that surfaced four more independently-real, general compiler bugs, each found by chasing the previous one:

- **Explicit-body property getters were silently discarded** (`parse_auto_property_body`, `src/parser/declarations.rs`): `{ get { return this.Field; } }` and `{ get => expr; }` (the accessor-level arrow form, as opposed to the already-working top-level `Prop => expr;` expression-bodied form) parsed and *threw away* the accessor body, always creating a meaningless auto-property backing field instead — so any getter with real logic silently returned a default/zero value. This is a serious, general bug: `DbQuery<T>.Count`'s loop-based getter, and an entire `SqlConnection` class in `System.Data.SqlClient.gl` whose `ConnectionString` setter's side effects (`ParseConnectionString(value)`) were silently dropped, were both already latently broken by it. Fixed with a new `parse_property_accessors` that returns what each accessor actually contains; when a property is getter-only with a real body, it now synthesizes a real `get_{name}` method (the same dispatch property reads already use for the working arrow form) instead of a backing field. Scoped conservatively: any property with a setter or a mixed accessor combination still falls through to the pre-existing (auto-property) behavior, unchanged — extending real setter-method dispatch (needed for `SqlConnection`-style cases) is separate, not-yet-done follow-up work.
- **`double` → integer casts were entirely unimplemented** (`cast_value`, `src/llvm.rs`): the reverse direction (`int` → `double`, `sitofp`) existed, but explicit `(int)someDouble`/`(long)someDouble` (needed for `TimeSpan`/`DateTime` millisecond arithmetic) had no `fptosi` case at all and errored outright. Fixed by adding the truncating (round-toward-zero, matching C# cast semantics) conversion.
- **Whole-number `double` literals produced invalid LLVM IR** (`TypedExprKind::Float`, `src/llvm/stmt_expr/expressions.rs`): Rust's `f64::to_string()` omits the decimal point for values like `86400000.0` (prints `"86400000"`), which LLVM's IR parser then reads as an *integer* literal — a hard type-mismatch error wherever a `double` operand was expected. Fixed with a new `format_double_literal` helper (`src/llvm/helpers.rs`) using LLVM's hex-float form (the value's raw bits as `0x` + 16 hex digits), which sidesteps decimal-formatting ambiguity entirely and is exact for any finite value.
- **`DateTime` had been silently hardcoded to `string` at parse time this entire project** (`src/parser/expressions.rs`): a `DateTime`-typed declaration parsed straight to `TypeSyntax::String`, regardless of what `System.gl` actually declared `DateTime` to be — a "just treat it as its serialized form" shortcut that predates this session and made a real `DateTime` class fundamentally unreachable no matter how it was implemented. Found by bisecting a "field target has no object layout: String" error down to a two-line reproduction with a user-defined class literally named `DateTime`. Removed the hardcoding so `DateTime` resolves as an ordinary class type; `Guid` has the identical shortcut and was deliberately left alone (out of scope, not requested).

With that unblocked, implemented for real:
- **`DateTime`** (`packages/System/System.gl`): backed by a single `long UnixMillis` (milliseconds since the Unix epoch, UTC) — real `UtcNow`/`Now` (via a new native `System_DateTime_UtcNowMillis_Native`, `src/runtime.rs`), `MinValue`/`MaxValue`/`UnixEpoch`, `Year`/`Month`/`Day`/`Hour`/`Minute`/`Second`/`Millisecond`/`Date` (via new native calendar-math helpers implementing Howard Hinnant's `days_from_civil`/`civil_from_days`, public-domain proleptic-Gregorian conversion), `Add`/`AddDays`/`AddHours`/`AddMinutes`/`AddSeconds`/`AddMilliseconds`/`Subtract`, `CompareTo`/`Equals`, real `Parse`/`TryParse` (a permissive ISO-8601-ish parser) and `ToString` (real ISO-8601 formatting) — all via new native functions, not stubs.
- **`TimeSpan`** (`packages/System/System.gl`): the pre-existing `FromMinutes`/4-arg-constructor were bugs in their own right (silently ignored their arguments, always producing a zeroed span) — fixed alongside `FromDays`/`FromHours`/`FromSeconds`/`FromMilliseconds` and `TotalDays`/`TotalHours`/`TotalSeconds`/`TotalMilliseconds`.
- **JSON serialization of `DateTime`** (`emit_json_serialize_datetime`, `src/llvm/endpoint.rs`): a `DateTime`-typed field now serializes as its quoted ISO-8601 string (matching real `System.Text.Json`), not as a nested object exposing the internal `UnixMillis` field the way an ordinary class would.
- **`DbSet<T>.Include`/`ThenInclude`** (`packages/Microsoft.EntityFrameworkCore/Microsoft.EntityFrameworkCore.gl`): added, delegating to `AsQueryable()` first (mirroring the existing `Where`/`Count` pattern) instead of falling through to the untyped no-op fallback.
- **`DbQuery<T>` real `Skip`/`Take`/`OrderBy`/`OrderByDescending`**: added, via a new `FilteredRows()` helper that applies the current predicate eagerly (ordering/pagination are position-based and don't compose as a lazy predicate the way `Where` does); `OrderBy`/`OrderByDescending` take a `Func<T, DateTime>` key selector (the shape every real call site in this codebase needs) and insertion-sort by `.UnixMillis`, sidestepping any need for operator overloading on `DateTime` itself.
- **`DbQuery<T>.Where` now composes with AND instead of replacing**: previously, each `.Where(...)` call discarded the prior predicate entirely, so `List.QueryHandler.Handle`'s chained tag/author/favorited filters would have silently kept only the last one applied. Fixed via a closure capturing both predicates. (Not yet confirmed as a *live* bug against the real app — none of those `Where` branches execute for the empty-query-string case tested — but a real, independently-confirmed one nonetheless.)

Verified via native repros for each piece (short-circuit-adjacent property-getter cases, casts, the exact DateTime/TimeSpan API surface — every computed value checked against the expected real answer, including a full ISO-8601 round-trip through `Parse`/`ToString`) and the full `cargo test` suite: 309 passed, 0 failed, 1 ignored, zero regressions despite touching the parser, casts, and literal formatting.

**New finding, not fixed this slice**: `GET /articles` on the live app is unchanged at `{"Articles":null,"ArticlesCount":0}` despite all of the above — none of it was actually the root cause for *this specific* symptom. Traced (via a two-line repro: a method declared to return an unresolvable interface type, whose body returns a real, resolvable struct value) to a more fundamental gap: a variable's static type is fixed to whatever a method's *declared* return type resolves to, and `IQueryable<T>` has never been declared as a real interface anywhere in this codebase — it's `Unknown("IQueryable<T>")` in `ArticleExtensions.GetAllData()`'s case, regardless of what `DbQuery<T>` value the method body actually returns. Every further LINQ call on such a variable resolves through the compiler's opaque/unknown-type fallback (a silent no-op that produces null), independent of whether the underlying concrete methods (now fixed, this slice) work correctly. The real fix is declaring `IQueryable<T>` as a real interface and making `DbQuery<T>`/`DbSet<T>` implement it, routing through the compiler's interface-dispatch machinery already used for MediatR/DI (Slices 1/6) — except those are all *class* interface implementations, and `DbQuery<T>`/`DbSet<T>` are *structs*, so this needs struct-implements-interface dispatch, which may itself be new ground. Deliberately not started, given how much scope this session already covered — flagged for a dedicated slice with its own scoping pass.

### Slice 9 — Made `IQueryable<T>` resolve to its real underlying type across a method boundary (August 2026)
Scoped from Slice 8's finding. The Slice 8 write-up above speculated the fix would need declaring `IQueryable<T>` as a real interface with struct-implements-interface dispatch (unexplored ground). That speculation turned out to be wrong — the actual root cause was much narrower and needed no new dispatch mechanism at all.

- **Return-type inference for the one safe case**: added `infer_iqueryable_return_types` (`src/tir/signatures.rs`, called from `TypedProgram::lower` in `src/tir.rs` right after field population, before the main per-type lowering loop). For any function/method declared to return `IQueryable<T>` with a body that is a single `return expr;` (covering both explicit-block and arrow-expression bodies, which desugar to the same shape), it independently lowers `expr` against a scope built from the declared parameter types and, if that resolves to a concrete (non-`Unknown`) type, overwrites the signature's `return_type`/`return_ownership` in place — leaving every other case (multiple returns, a body that doesn't resolve, non-`IQueryable` returns) untouched. This is what let `ArticleExtensions.GetAllData()`'s declared `IQueryable<Article>` resolve to a real `DbQuery<Article>` at all, rather than the permanent `Unknown("IQueryable<Article>")` every caller previously saw.
- **The actual, deeper bug**: even with the signature above correctly inferred, every *chained* call on the resulting value (`.Include(...)`, `.Where(...)`, `.AsNoTracking()`, ...) still came back as the unspecialized `DbQuery<T>` instead of `DbQuery<Article>` — confirmed by instrumenting the resolution path and walking the actual call chain's `TypedExpr` tree: `resolve_specialized_method_call_signature` (`src/tir/signatures.rs`), which drives class-level generic substitution via `generic_owner_subst`, was correctly computing `DbQuery<Article>` at every single step (verified directly, before/after). But the general call-lowering site that consumes its result (`src/tir/lowering.rs`, the member-call branch of `lower_typed_expr_with_expected`) then **unconditionally overwrote** that correctly-specialized type:
  ```rust
  let ty = resolved_signature.as_ref().map(|signature| {
      substitute_generic_args_in_ir_type(&signature.return_type, &signature.generic_params, &generic_args)
  }).unwrap_or(ty);
  ```
  `resolved_signature` here is found by matching `signature.symbol` against `candidates` — a list built from the *raw*, unspecialized `env.methods` lookup a few lines above — and `substitute_function_signature` (the class-level substitution helper) always preserves `symbol` unchanged across specialization, so this symbol-match *always* lands back on some unspecialized candidate whose `return_type` still carries the owning class's own bare generic-parameter placeholder (`DbQuery<T>`), regardless of which concrete instantiation actually produced the call. `generic_params`/`generic_args` here are for the *method's own* generics (e.g. `Foo<U>()`) — completely orthogonal to the owning class's generics, and empty for a plain method like `Include`. So the "substitution" was a no-op that discarded the correctly-specialized `ty` and replaced it with the raw, unspecialized one from `candidates` — silently re-erasing every chained call back to `DbQuery<T>`, self-consistently, for the rest of the chain (each subsequent call's own `generic_owner_subst` then computed a garbage identity substitution `{T: Unknown("T")}` from the already-wrong receiver type, so the corruption was completely stable and easy to mistake for "expected" behavior when read in isolation).
  Fixed by substituting into the already-specialized `ty` (from the general resolution path just above) instead of the raw `signature.return_type`: `substitute_generic_args_in_ir_type(&ty, &signature.generic_params, &generic_args)`. This is a strict improvement in every case — when the method has no generics of its own the substitution is now correctly a no-op (matching `ty`, not clobbering it), and when it does have real method-level generics, they now layer correctly on top of the already class-specialized base type instead of on top of the raw unspecialized one.
- Verified via instrumented before/after tracing of the full `context.Articles.GetAllData()` → `.Include(...)` → `.Include(...)` → `.Include(...)` → `.AsNoTracking()` chain from the real `List.QueryHandler.Handle`: every step now carries `Struct("DbQuery<Article>")` end-to-end, not just the first call. All temporary debug instrumentation was removed before landing.

Verified via the full `cargo test` suite: 309 passed, 0 failed, 1 ignored, zero regressions — plus `cargo run --bin realworld_smoke`, which now gets past `GET /articles` (HTTP 200) and only fails on the already-documented, unrelated Swagger gap.

**Two new findings, not fixed this slice**, both confirmed independent of the fix above and of each other:
- `GET /articles` against a genuinely empty database still returns `{"Articles":null,"ArticlesCount":0}` rather than `{"Articles":[],"ArticlesCount":0}`. This is *not* the Slice 8/9 erasure bug recurring — checked directly: `DbSet<T>`'s query methods (`AsQueryable`/`Where`/`Include`/`AsNoTracking`) all null-guard `this.Items` and always produce a real, non-null (possibly 0-length) `List<T>` for `DbQuery<T>.Rows`, and `DbQuery<T>.ToListAsync()` always allocates a fresh `List<T>` before its filter loop runs, so a real, non-null, empty list should reach `ArticlesEnvelope.Articles`. `emit_json_serialize_list` (the JSON codegen, Slice 7) was also re-checked and only emits `"null"` when the list pointer itself is actually null. The live app's actual seed/persistence path was not reachable to test directly — `POST /users` returns `501 Not Implemented` (a separate, unrelated gap), so there is currently no way to get a real row into `ConduitContext.Articles` through the live HTTP API to confirm whether this is an async `Task<List<T>>` result-materialization bug, an object-initializer-vs-default-property-initializer (`List<Article> Articles { get; set; } = new();`) ordering bug, or something else. Root cause not identified — flagged for a dedicated slice.
- **Primitive numeric `.ToString()` has no implementation anywhere and crashes at runtime.** Confirmed via a minimal repro (`int c = 5; c.ToString();`) failing even in complete isolation, no object/list/async involved. `resolve_method_call` (the free function in `src/tir/call_resolution.rs` that resolves member-call expressions) has no match arm for `(IrType::Byte | Short | Int | Long | UInt, "ToString")` (nor for `Double`/`Bool`), so it falls through to the final wildcard arm, which resolves the call to a literal, unmangled symbol named `ToString` — the same class of bug the Slice 9 chain-erasure symptom resembled before this slice's fix (an unresolved bare-name call target), except this one is genuine: no implementation exists to link against at all, so the process crashes at that call. Not a regression from this slice or Slice 8 — confirmed pre-existing (the runtime helpers this would need, `glitch_i64_to_string`/`glitch_double_to_string`, already exist and are used directly by JSON serialization codegen, which is why this was never hit by that path) and apparently never previously exercised by any existing test or app code path (no `cargo test` case calls `.ToString()` on a primitive and actually runs the result). Flagged for a dedicated slice — needs deciding how a builtin instance-method call like this should wire to a runtime symbol (matching the existing `System_Console_WriteLine_*`-style static-function pattern, or something new).

## Summary
The compiler now has concrete generic layout specialization, specialized generic methods, and safe lowering for constrained placeholder indexing. What remains is the runtime and framework surface that still falls back to warnings or typed defaults: package dispatch, ASP.NET-style host behavior, async/runtime breadth, and the remaining EF/DI compatibility markers. The RealWorld (Conduit) app now compiles, boots, and serves `GET /articles` with a well-formed JSON response, without crashing (Slices 6, 7, and 9), the Conduit IntegrationTests project bundle compiles cleanly end-to-end (Slice 6), endpoint responses can be real nested JSON with correct null handling including real `DateTime` formatting (Slices 7–8), MediatR dispatch resolves correctly across namespace-colliding nested types (Slice 1), DI-registration-aware interface resolution handles bundles with multiple implementations of one interface (Slice 6), `&&`/`||` genuinely short-circuit (Slice 7), `DateTime`/`TimeSpan` are real (Slice 8) — along with property-getter parsing, `double`→int casts, and double-literal-formatting bugs Slice 8 found and fixed — target-typed `new()` — plus the constructor-registration, memory-leak, type-merging, and double-qualification bugs it led to — is fully resolved (Slice 5), and `IQueryable<T>` query-chain return values now keep their real, fully-specialized type across method boundaries instead of erasing back to a bare generic placeholder on every chained call (Slice 9). Two narrower gaps remain, both newly confirmed and neither yet started: the live app's empty-result JSON still reads `Articles: null` instead of `[]` (root cause not yet identified), and primitive numeric `.ToString()` has no implementation at all. Real Swagger/OpenAPI generation remains open beyond that.
